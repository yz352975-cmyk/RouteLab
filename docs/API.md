# RouteLab v0.3 Python 接口

入口保留为 `def solve(ctx)`。全局模式仍返回完整路线；新分布式模式让同一份程序在 A～G 各自的命名空间中执行，每个路由器独立维护表和状态。

## 全局模式：保持 v0.2 行为

```python
# ctx["mode"] == "global"
# ctx: {"from": "A", "to": "F", "graph": [{"a":"A", "b":"B", "cost":2, "up":True}, ...]}
def solve(ctx):
    return ["A", "B", "C", "E", "F"]
```

开场使用原来的七节点拓扑，校验物理链路、禁行、环路和最小总代价。下一次事件进入环形试验拓扑，并收回全局图。此后 `ctx` 不包含 `graph`、完整链路或其他节点的表。

## 分布式模式：两个阶段

`ctx["mode"] == "local"`，以 `ctx["phase"]` 区分调用。算法不会被引擎替你计算：路由表来自你返回的 `table`，消息来自你返回的 `advertise`。

| 字段 | 含义 |
|---|---|
| `current` / `destination` | 当前路由器、数据包目标 F |
| `time` / `elapsed` | 全局仿真时隙、距当前事件起点的时隙数；没有真实时间单位 |
| `neighbors` | 仅直接邻居的 `to, cost, up, allowed, authenticated` |
| `neighbors[].estimate` / `estimate_age` | 最近实际收到的原始通告中到 F 的距离、距收到的时隙；未收到时为 16 / None。可能过期、乱序或不可信，不是最短路预言器 |
| `table` | 本路由器上次提交的表，冷启动只有自己的距离 0 |
| `inbox` | 本时隙实际送达本机的消息；update 可见，forward 为空 |
| `state` | 本机自己的可变字典，仅存 JSON 可序列化数据；两个阶段的修改都会保留 |
| `infinity` | 16；任何候选距离都应饱和到 16 |
| `period` / `max_delay` / `route_timeout` | 教学用周期、最大消息延迟和建议缓存超时；是否使用由程序决定 |
| `stable_for` | 本机提交的整张表连续未变化的时隙，不代表全网已经收敛 |
| `ttl` | 数据包剩余跳数；update 中的值仅为接口默认值，forward 中为当前实际值 |

update 阶段返回：

```python
{
    "table": {
        "A": {"metric": 0, "next_hop": "A"},
        "F": {"metric": 3, "next_hop": "B"},
        "G": {"metric": 16, "next_hop": None},
    },
    "advertise": {  # 可省略；不提供就不发送消息
        "B": {"A": 0, "F": 16, "G": 16},  # 可以按邻居做反向毒化
        "D": {"A": 0, "F": 3, "G": 16},
    },
}
```

- `metric` 是 0～16 的有限数值，不能使用 `float('inf')`、NaN 或负数。自己的表项固定为 0；引擎校验格式，不替你推导路由。
- `next_hop` 是直接邻居、自己或 None。错误地保留失效下一跳不会被悄悄修复，而会在转发中失败。
- 每次 update 产生的 `advertise` 只发送一次。触发更新、周期发送和不发送的时机均由程序选择。
- 每个发送方/接收方每时隙最多一份向量，每份最多 64 项。发送给断开的邻居会被丢弃。
- `table` / `inbox` 是本机输入副本，修改它们不直接改引擎；通过返回值提交表。`state` 的修改会提交。

一份 inbox 消息示例：

```python
{
    "id": 28, "sender": "B", "receiver": "A",
    "sent_at": 5, "deliver_at": 8, "seq": 5,
    "vector": {"B": 0, "F": 2},
    "authenticated": True, "epoch": 0,
}
```

`seq` 是模拟器生成、随发送方 update 轮次增长的序号。引擎不会替玩家拒绝旧消息。`epoch` 用于仿真器丢弃已经跨越链路断开/修复的在途消息，不是普通路由器获得的完整拓扑信息。

forward 阶段：

```python
def solve(ctx):
    if ctx["phase"] == "forward":
        row = ctx["table"].get(ctx["destination"], {})
        return row.get("next_hop") if row.get("metric", 16) < 16 else None
    # 在这里处理 inbox / state，重新计算 table 并返回 advertise。
```

`None` 表示游戏暂缓本次注入/转发，控制面仍继续运行，观察预算继续消耗。最多观察 160 个转发时隙，等待不消耗 TTL；每成功经过一条链路消耗一个 TTL，初始 TTL=12。没有 `visited` 阻止回访，因此可以观察实际转发环路。

## 每个时隙的顺序

1. 执行已安排的物理故障/修复。
2. 按 `(deliver_at, id)` 送达消息；同到达时间按发送入队先后处理，较新消息可能先到。
3. 各路由器以自己的表、直接链路和收件箱调用 update。
4. 提交表、排入新消息。新发送的消息最早下一个时隙送达。
5. 转发观察阶段，在数据包当前节点调用 forward；控制面仍同时推进。

端点立即知道本地链路 up/down，远端不接收“某处已断线”的全知广播。节点要靠相邻通告、超时及自己的更新规则学习变化。

## 成功、重试与延续

观察器在数据包到达 F 后检查：各正常且获准的节点到 F 的表项等于当前合法最短距离，有限路由的下一跳满足该距离；全网表至少稳定 `2 * max_delay + 4` 时隙；没有尚未执行的物理事件。失败会解释表项或观察时间问题。这是教学验收，不是任何路由器可调用的收敛查询，也不是对任意未来消息的数学保证。

成功的表、状态、消息队列和仿真时间成为下一次事件的起点。失败结果仅用于观察；再次运行从同一事件起点重放，避免一次失败改变下次试验的条件。自动推进从不改编辑器。模块级全局变量在一次运行中各路由器独立，但下次执行会重新加载；需要延续的数据请放在 `ctx['state']`。

同一会话种子、事件起点、代码和 Python 版本产生相同的引擎调度。程序自身使用真实时间、随机数或外部文件仍可能引入不确定性。

## 示例与旧接口

`examples/distance_vector.py` 是可选参考：缓存邻居向量、Bellman–Ford 重新计算、周期/触发通告、超时、反向毒化、顺序检查、策略与来源过滤。设置 USE_POISON=False、SPLIT_HORIZON=True 可以实验水平分割，观察给不同邻居的向量省略了哪些目标；反向毒化则显式通告不可达。观察等待窗口是教学方法，不是通用收敛证明。可通过 GUI“参考代码”明确载入。

`World(..., protocol='legacy')` 默认值及旧 `ctx_for` / 下一跳验证器保留给 v0.2 的直接 API 使用者；`tests/fixtures/` 冻结了原版程序。GUI 的所有分布式事件都使用 `protocol='dv'`，不会走旧的固定距离估计分支。旧字符串程序要升级为双阶段协议；原来的函数名和全局算法继续可用。

执行环境只适合可信代码。逻辑上的独立上下文不是安全隔离；Python 代码仍有本机进程权限，见 README。

## v0.4 跨运营商规划任务

当 `ctx["mode"] == "carrier"` 时，返回从 `ctx["from"]` 到 `ctx["to"]` 的站名列表。这里模拟云渡区域网根据已知合同规划单向服务路径。目的地始终是蓝港数据中心 F；没有 BGP 会话、AS_PATH 传播或完整的商业选路协议。

读取 `owners`、`operators` 和 `links`。每个出口的 a→b 是有向的。先检查 up 和通告 origin（应等于 destination_owner）。internal 表示网内；transit 允许转接并计费；peering 仅允许访问接收方自己的目的地，要求 owners[b] 等于 destination_owner。竞争通过具体合同到期和定价体现。

在可达路线中最小化 objective 指定的累计指标。cost 使用 cost + fee，delay 使用 delay + congestion（毫秒），risk 使用教学用可加风险分。每种目标均允许同分的任一合法路径。失败反馈与动画只使用实际通过的前缀。状态按十次事件的顺序累积，同一事件重试不会变更报价。随后的自由演化使用会话种子，一次调整一个合同或链路。

## 服务可用性事件 S1

每一窗调用一次 `solve(ctx)`。可以在已有函数内按 `ctx["mode"] == "service"` 分支处理。入口只提供汇总统计；真实请求分类仅由模拟器用于结算。输入副本中的修改不会写回模拟器。API 隔离属于游戏规则，执行不可信 Python 仍需要独立操作系统隔离。

- 输入包含 time、capacity（处理容量）、bandwidth（入站上限）、buffer（队列上限）、queue（窗首积压）、sources 和最近三窗的 history。sources 按站名提供运营商、requests 和 repeats；正常玩家也可能重复访问。
- 返回字典，可选 limits（每站总配额）和 repeat_limits（每站重复访问配额）。键是 B、C、D，值为 0～100 的整数。省略代表不限；两个配额同时生效，每窗重置。
- 评估窗口内，正常请求完成率至少 85%，异常请求完成比例至多 30%，平均窗末积压不超过 4。过滤、容量丢包与仍在排队分别计数。平均等待只统计该窗已完成的请求。运行反馈对比同一种子的无策略基线。
- 所有请求都是本地队列中的模拟记录。真实流量通常没有准确的真值标签，教学模型中的重试特征不构成现实攻击归因。

## 正常活动与误封 S2

S1 成功后，编辑器代码原样进入 S2。每窗处理容量为 20。多个正常会话集中重试，同时另一个入口存在少数会话的重复负载。活动期间热点会换入口。仍使用 service 模式和相同的配额 API；新增 `sources[站名]["sessions"]` 表示该窗去重会话数。最近三窗的 history 包含各入口当时的 sources。应同时支持 S1 的代码可按 incident 判断新增字段是否存在。

在服务可用性的三项目标之外，要求误封率（被配额拦下的正常请求 / 全部正常请求）不超过 10%，漏放率（穿过配额的异常请求 / 全部异常请求）不超过 30%。分母仅统计事件发生后的窗口。容量丢包和策略过滤分别记账。
